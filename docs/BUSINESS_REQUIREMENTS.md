# CAXA 图纸工具业务流程与需求

更新时间：2026-11-20

本文是跨会话、跨窗口的业务规则基线。新会话在优化、重构或处理外部评审
意见前，必须先阅读本文、`docs/HANDOFF.md` 和 `docs/IMPLEMENTATION.md`。

## 1. 规则优先级

1. 用户在真实业务现场确认的规则优先于架构建议、代码审查和通用最佳实践。
2. 本文标记为“刻意设计”“兼容回退”“不得移除”的内容，不是待修 bug。
3. 外部评审提出相反意见时，先对照本文和真实 CAXA 行为；不能仅因代码看起来
   冗余、复杂或“不符合最佳实践”就删除。
4. 新规则、例外和原因必须同步写入本文，并在需要时补回归测试。
5. 未确认的评审建议放入“待确认事项”，不得直接实施。

## 2. CAXA API 兼容策略

- CAXA 2011 的高层对象 API 在某些客户端/权限/对象状态下会返回空、
  抛出异常、复用错误关系或只完成部分写入。因此保留“高层 API 失败后尝试
  低层对象库 API”的兼容路径。
- 高层失败后走低层回退是刻意设计，不应作为冗余代码删除。
- 多父级借用使用低层 `NewOneLevelLink(1037, parent, child)` 直接插入独立
  Part2Part 关系。不能“简化”回高层 `LinkSubPart`，否则同一子件借给第二台
  上级时可能复用或移动第一条关系。
- `PlmComApi.dll` 按设备注册一次，不再每次登录探测：
  - 每台新设备首次上传前强制调用 32 位 `SysWOW64\regsvr32.exe`，必要时请求 UAC；
  - 注册成功后把设备标识和持久化 `registration_id` 写入本机
    `journal.sqlite3` 的 `device_state`；
  - 后续上传不再包含 COM 检查或注册代码；
  - 数据库被复制到另一台设备时不沿用原设备标记；
  - 注册/UAC 失败不写标记，下次仍会重试；
  - 需要强制重新注册时设置环境变量 `CAXA_FORCE_PLM_REGISTRATION=1`。
- 每批关系写入完成后必须整批回读；任一计划边缺失时补建，仍缺失则阻止流程。
- 写操作结果无法确认时标记“待核实”，不得自动重放。
- 已发布图纸不能通过追加版次静默改为复用；必须明确失败。

## 3. 当前用户与账号

- 常规图纸上传测试使用测试账号账号。
- 部门主管/审核人为审核账号。
- 密码使用本机 DPAPI 配置复用，不写入源码、文档、日志或 Git。
- 审核快速处理工具必须使用审核账号账号。

## 4. 文件名与对象分类

- 数字图号图纸：`图号 名称.pdf`，图号和名称之间一个空格。
- 单字母工艺文档：`Z02.*`、`Z03.*`、`J03.*`、`M03.*`、`P03.*`、
  `T03.*` 等，文件名不带中文名。
- `02.*` 是半成品 Part，归属 Product `02 半成品`；其工艺文档可使用
  `Z02.*` 并挂到对应半成品 Part。
- `03.*` 是整机，归属对应系列 Product；`Z03.*` 挂到整机 Part。
- `01.*`、`04.*` 等其他普通组件按图号关系归属或借用。
- `ZJ03.*` 等多字母前缀仍按当前规则拒绝，除非用户另行确认。

## 5. Part 与关系

- 同一图号的原始 Part（原件）在 CAXA 中只能存在一个。不同上级需要复用该
  Part 时只能建立 `reference=True` 借用关系，不能为每个上级重新创建归属原件。
- 预检发现图号已作为 Part 存在时，即使上传计划当前是“归属子件”，也必须
  改为借用该已有原件。
- 若同一图号已经查到多个 Part，说明数据库已违反原件唯一规则；预检和上传
  必须阻止，并列出重复图号，不能任选其中一个继续操作。
- 已有原件行提供“只升版”复选框：
  - 勾选：只给已有原件追加 Drawing 版本，不执行任何归属/借用关系；
  - 不勾选：先升版，再按上传计划中的父级建立借用关系；
  - 默认值：图号没有任何计划关系时为勾选；存在计划关系时不勾选；
  - 不勾选但没有任何借用父级时，上传必须在上传任何写入前阻止。
- 普通 Part 最多一个 `reference=False` 归属父级。
- 同一个 Part 可以有多个 `reference=True` 借用父级。
- 同一 `01.x.*` 系列内的父子关系默认归属；跨系列默认借用。
- `03.*` 整机下组件、跨图号复用等为借用。
- 人工选择优先于自动图号判断。
- 借用关系只链接已有节点，不能为了建立借用而新建缺失子件。
- 手动 `link_only` 条目缺失时报错，不创建 Part。

## 6. Product 与系列目录

- Product `01` 是通用件，Product `02` 是半成品。
- `03.*` 整机位于各自系列 Product，不放在 Product 01。
- 上传端**不允许创建系列目录 ProductFolder**。自动识别或人工指定到的系列路径
  必须已经在 CAXA 设计树中存在；不存在时预检和上传都必须在上传任何图纸、
  Part 或 Product 前报错。
- 目标系列目录已存在时，Product 已有则复用；Product 缺失时仍可按整机图号和
  用户填写的产品名称新建，并挂入该既有系列目录。
- 只有 `J03/M03/P03/T03/Z03` 等工艺文档、没有对应 `03.*` 整机图时，预检仍必须
  根据工艺文档的 `machine` 识别目标整机。若 Product 或整机 Part 不存在，应生成
  `系列目录（既有）→ Product（可新建）→ 整机 Part（可新建）` 三级结构，再把
  工艺文档挂到整机 Part。创建整机 Part 不得依赖本批存在整机图。
- `02.*` 与 `03.*` 的工艺文档都必须受支持。`J02/M02/P02/T02/Z02` 等挂到
  Product `02 半成品` 下的 `02.x.*` 目标 Part，不能套用 03 的系列产品名称规则。
- `02.A36.02.AR02` 等目标按点号层级从最近上级 `02.A36.02` 向上查找已有
  Part。末级缺失时，helper 只创建末级并挂到最近的既有上级；不得直接挂到
  Product `02 半成品`，也不得创建新的 `02.x` 分组。Product `02 半成品`、
  点号上级缺失或同一图号存在多个 Part 原件时，预检和上传都必须阻止。
- Product 缺失时，系列产品名称必须可在对应工艺文档行填写并作为上传计划保存；
  仅整机 Part 缺失而 Product 已存在时，不需要重复填写产品名称。
- 系列行、产品行的右键改名只修改本地上传计划，不修改已有 CAXA 对象。
- `HT合同特殊/HGB系列` 是二级 ProductFolder 路径，不是特殊对象类型。

## 7. 物料编码

- Part 的“物料编码”必须等于该 Part 的图号，即 CAXA 属性 `MaterialNo`。
- 新建和复用 Part 都要校验物料编码；不一致时更新并回读确认。
- 上传 `Z03.*` / `Z02.*` 工艺文档时，不能把工艺文档编号写入 Part 物料编码。
  - 03 整机 Part 使用 `03.*` 整机图号。
  - 02 半成品 Part 使用 `02.*` Part 图号。

## 8. 上传与流程

- 上传内容始终使用任务暂存副本，不能因本地文件改名而上传错误内容。
- 重复图号默认“在现有版本上追加新的版次”。自动确认必须限定在本次 upload
  命令执行期间、**本 helper 进程**内，并通过精确标题
  `对象已经存在提示框`、正文“在数据库中已经存在”、选项“追加新的版次”
  和当前目标文件名共同匹配。不得跨进程点击用户手动发起的弹框。
- 重复框的选项、`应用到所有`和`确定`必须通过 UI Automation 操作真实
  RadioButton/CheckBox/Button，并回读选中状态；不能用文本标签的
  `BM_CLICK` 代替。升版后先刷新 EAP 实体，仍读到旧版次时重新登录新 helper
  会话只做只读复核，绝不重放上传写入。
- 反审后图纸即使仍有旧的 `WFProcessInst` 关系，只要当前状态已回到“设计”，
  仍允许追加版次。不得仅凭流程关系阻止；CAXA 反审本身会先创建新版本，
  现场已确认随后继续追加可以成功。
- 关系、文件或类型验证不完整时，不能发起审核打印流程。
- 审核打印流程必须关联本批已确认的全部文档：Drawing（`1002`）以及
  CappDocument（`1003`，如 J03/M03/Z03）。不能只筛 `1002` 而漏掉工艺文档。
- 固定审核打印参数：
  - WFTemplate `1`
  - WFProcessTemplate `31`
  - process_def_id `2`
  - activity_def_id `4`
  - 审核人 Person `66` 审核账号
- 当前 02 半成品测试图纸上传后，由用户人工检查并手动发起流程；不要自动
  通过旧上传 helper 发起。

## 9. 性能约束

- Product 查找优先按 `IdentityNo` 精确查询，不递归扫描整棵产品树。
- 自动 own/borrow 由图号结构决定，不逐条扫描设计树。
- 同一任务缓存 Part、整机 Part 和 Product 查询结果。
- 性能优化不得删除上述兼容回退或关系最终回读。

## 10. 审核快速处理工具（独立）

- 部门主管需要快速处理图纸审核，使用审核账号账号。
- 该功能不得加入现有上传 helper；应作为独立工具交付。
- 已确认 CAXA 工作流 DAL 暴露以下工作项动作：
  - `CxDalWfWorkItem.pick(workitem_id)`
  - `CxDalWfWorkItem.complete(workitem_id)`
  - `CxDalWfWorkItem.submit(workitem_id, submit_type)`
  - `CxDalWfWorkItem.submit_to(...)`
  - `CxDalWfWorkItem.reject(...)`
  - `CxDalWfWorkItem.retake(...)`
- 2026-11-09 已通过真实审核抓包确认：
  - Workflow Server 使用 `8903/tcp`；
  - 审核账号 Person ID 为 `66`，DCC Person ID 为 `8`；
  - 接收任务调用 `CWfWorkItemStub.Pick(workitem_id)`；
  - 审核通过调用
    `DesignateNextPerformer(workitem_id, "2", "5", 1, "8")`，
    再调用 `Submit(workitem_id, "通过")`；
  - 审批成功后工作项 `state=3`、`submit_mode="通过"`；
  - `WFWorkitem` class ID `2468`，流程 class `2466`，活动 class `2467`，
    流程-文档关系 class `3305`。
- 独立初版工具位于工作区 `supervisor_review_tool/`，未加入上传 helper。
- 初版用 `WFWorkitem(state=2) + participant + 父流程(state=2)` 查询，
  仍会带出历史开放任务；后续 agent 应还原 `WfTaskBox.dll` 的
  `GetUnPickedTask/GetPickedTask` 过滤逻辑。
- 独立工具的分步按钮必须保持“接收 → 发布全部图纸 → 通过并转 DCC”的真实业务顺序。

## 11. 上传列表界面

- “核实待定结果”必须使用业务名称：图纸上传、次级/借用关系、审核打印流程。
  有图号时直接显示图号；关系显示父级与子级；流程优先显示流程实例 ID、
  流程状态和关联文档数。界面不得显示 `upload`、`relation`、`workflow` 或
  `upload:stage` 一类内部代号。
- 完整编辑对话框中的“系列产品名称”“系列产品目录”可显示灰色示例文字，
  但示例不属于字段值，不得写入 manifest，也不得参与上传。
- 右键“从列表中删除所选图纸”只修改当前上传计划：
  - 支持当前选中的一条或多条图纸行；
  - 同步清理 `items`、`relations`、`manual_borrows` 和当前 bundle 中的对应字段；
  - 图纸作为父级或子级的归属、借用关系必须一起清理，不得留下悬空关系；
  - 同步清理不再有来源图纸的产品名称必填状态和当前产品选择引用；
  - 不删除本地 PDF，不删除 CAXA 远端 Drawing、Part、Product 或关系对象；
  - 系列目录、产品计划节点和外部 CAXA 节点不是图纸，不得作为图纸删除。

## 13. 2026-11-13 用户确认的评审边界

- CAXA 重复对象弹框的默认选项就是“追加新的版次”；切换到其他选项才需要
  额外确认。本次修复保留现有自动确认行为，不因通用评审假设增加确认或等待。
  既有 helper PID、目标文件名和上传作用域约束继续保留。历史文档中对选项
  操作的描述不能作为否定该默认业务行为的依据。
- 图号唯一。同名 PDF 或不同来源同图号合并文件表示同一零件图纸或其升版，
  不会同时出现在同一处理批次。本次不改拆页/合并文件命名，不为不存在的
  并发来源冲突增加额外目录与交互。上传包内已有重复图号校验继续保留。
- 本次授权修复其余已确认的恢复证据、流程文档完整性、关系修复日志、
  helper 对象证据串用、工艺文档分类与上传包往返、总装图路径解析问题；
  性能优化必须保留内容校验、非幂等写不盲目重试和最终整批关系回读。

## 14. 2026-11-16 可操作的人工恢复与单独发起流程

- “核实待定结果”处理的是本机日志中状态为“执行中/待核实”的单条操作。
  待核实记录中的图号、目标文件名、关系端点和流程实例 ID 已足够用于定位业务对象。
- CAXA 的对象 ID、文档 ClassID（`1002/1003`）和流程关联文档 ID 属于后台数据，
  普通界面不显示，恢复窗口不得要求现场人员手工填写这些字段。
- 人工恢复必须采用以下流程：
  - 上传：程序按待核实图号和目标文件名找到宿主 Part 及其当前 Drawing/
    CappDocument，回读 Object ID、实际 ClassID、版次和文件名，再由用户确认。
  - 关系：程序按已知父级、子级和归属/借用类型回读真实关系，用户无需输入
    内部关系 ID。
  - 流程：优先使用日志中的流程实例 ID；日志没有时只允许用户填写 CAXA
    界面可见的流程实例 ID。程序自动回读状态和全部关联文档，并与本批文档集合
    严格比较。
  - 自动回读不唯一、不完整或类型/版次不匹配时，原操作必须保持待核实，
    不得猜测成功，也不得自动重放写入。
  - 确认未写入仍由用户业务判断；“成功”则由人工确认业务对象后，由程序生成
    完整后台证据。
- “核实待定结果”必须把当前任务日志中的待核实操作合并到一个窗口，避免每张
  图纸分别弹出确认框。窗口至少提供：
  - 自动回读所选操作并确认成功；
  - 确认所选操作未写入，解除待核实并允许回到主界面点击“开始上传”重试；
  - 全部确认未写入并直接重新上传当前计划。
- 上传功能区提供独立的“发起流程”按钮，用于上传成功后补发审核打印流程：
  - 只处理当前勾选、且在本机日志中已有确认上传记录和完整文档证据的图纸；
  - 不重新上传 PDF，不因本地 PDF 已移动或删除而阻止发起；
  - 任一所选图纸没有确认上传记录，或仍有关系未确认成功/待核实时必须阻止；
  - 使用界面中当前审核人，并沿用固定审核打印模板参数；
  - 与“上传完成后自动发起流程”复选框相互独立，不要求用户重新勾选该复选框。

## 15. 2026-11-17 已有原件与升版规则

- `.pdf` 后缀是当前正常文档名行为。2026-11-04 原图 `35759 a.1` 保存为无后缀，
  属于旧版本行为；当前 helper 会保留目标文件名后缀。
- 历史 Drawing 名称只是缺少 `.pdf`，且去掉后缀后与目标名称完全一致时，
  helper 必须通过图纸“属性编辑”等效接口自动补 `.pdf` 并回读确认，再继续
  重复检测和升版。该修复只允许补后缀，不得修改其他名称差异；补名失败则阻止上传。
- 判断“已有原件”必须按 Part 图号查询 CAXA 设计树，而不是按 Drawing 名称。
  旧 Drawing 名称可能因历史版本不带 `.pdf`，不能因此重新创建 Part。
- 预检和实际上传前都必须读取已有原件状态：
  - 预检结果在树中显示“已有原件”；
  - 归属关系强制转为借用；
  - “只升版”状态写入上传计划并在重复预检/重试时保持；
  - 实际上传不得只依赖 UI 预检结果，仍需在写操作前重新确认。
- 已有原件若已作为借用关系存在，重复执行应识别为已存在；不能创建新的
  Part 或把原件重新归属到新父级。
- “增加次级条目”对话框必须与双击编辑框一致，显示在 helper 主窗口中心。

## 16. 2026-11-17 CAXA 运行依赖与空密码

- helper 必须自行保证 CAXA EAP 运行依赖可解析，不能依赖现场机器 PATH
  恰好包含安装目录。设备注册和登录前必须把以下存在的目录前置到当前进程：
  - `CAXA EAP\1.0\bin`
  - `CAXA EAP\1.0\template\script`
  - 常见 CAXA PLM `CAXABOM\bin`、`CAXAEDM\bin`
- `PlmComApi.dll` 报“加载失败、找不到指定的模块”时，应先核对 DLL、
  32 位 CLSID 和依赖目录；文件存在不等于依赖完整。
- CAXA 用户名、服务器 IP 和端口必须填写；CAXA 密码允许为空串，以支持
  未设置密码的账号。密码为空时必须仍保存空凭据，不能沿用旧密码。
- 设备首次注册在缺少本机成功标记时，应先验证 COM 类是否已经可用；
  已可用则直接复用，避免重复 UAC 和 `regsvr32`。只有验证失败才重新注册。
- 03 Product 必须先按整机图号精确复用。未命中且用户填写系列产品名称时，
  必须按名称完全一致查找；同名候选必须用目标 ProductFolder 的对象 ID
  消歧。目标目录内仍存在多个同名 Product 时阻止并提示人工清理。

## 17. 2026-11-18 文件名规范化、02 半成品与批量核实

- “一键规范文件名”更新图号后，必须同步迁移上传计划中的父级、子级、
  手工借用端点和关系边；不能保留旧图号造成下一次 CAXA 预检出现悬空关系。
- 文件名中的 `Z02.*` / `Z03.*` 等成品代码是权威推导结果，规范化时必须覆盖
  行内旧的成品代码，避免错误成品代码继续参与预检。
- 02 半成品遵循与图纸相同的点号层级：`02.A36.02.AR02` 应从最近点号
  `02.A36.02` 开始向上寻找已存在的 Part 上级。助手只在已有上级下创建缺失的
  末级 Part，不得把 `02.x.*` 直接挂到 Product `02 半成品`。
- 同一 02 图号只能有一个原件 Part。多个产品/上级挂接是合法行为，但只能有
  一个 `reference=False` 非借用归属，其他挂接必须是借用。出现多个非借用归属
  时预检和上传阻止。
- 清理重复挂接时只能删除经验证的产品-零件或零件-零件关系对象，不得删除
  Part、Drawing 或 CappDocument。helper 发起关系删除时，确认框只允许在
  helper 自身删除作用域内自动确认。
- 人工确认待核实上传“未写入”后，原操作状态必须变为可重试，界面行恢复为
  “待上传”；用户可以回到主界面点击“开始上传”，也可以在合并窗口中直接选择
  “全部确认未写入并重新上传”。

## 18. 2026-11-19 上传端评审整改边界

- 本轮只改上传端；识图端和旧一体化识图界面暂不修改。
- 批次任务身份只由本次勾选执行的内容行决定。未勾选、已跳过或仅等待补录的
  行发生变化，不得改变已执行批次的任务身份，也不得导致已确认上传重新执行。
- helper 的 stderr 必须持续排空并保留有限尾部，避免子进程因管道写满阻塞；
  stderr 只能作为诊断证据，不能混入 stdout 协议。
- 待核实证据回读必须在后台线程执行。连接 CAXA、登录、回读和逐项验证不得
  阻塞 Tk 主线程；结果通过事件队列回到 UI。
- UI 事件处理发生异常后，事件轮询必须继续注册，不能永久停止；界面日志最多
  保留最近 5,000 行。
- `config.json` 必须采用临时文件加原子替换。写入失败时保留旧配置，不能留下
  截断文件。
- SQLite 日志继续保留 WAL，并设置有限 `busy_timeout`，避免上传端和恢复窗口
  偶发 `database is locked`。
- C# 写命令在可能已经写入后发生异常时，必须返回 `partial/uncertain`、阶段和
  已知对象/端点证据；Python 不得把这类结果当成可安全重放的普通失败。
- 同一账号登录提示的自动点击只允许在当前 helper 的 login 命令作用域和当前
  helper PID 内执行；无法证明归属时只记录，不自动点击。

## 19. 2026-11-20 版本号与 GitHub 分发

- 正式版本使用语义化版本 `vX.Y.Z`。版本号由根目录 `VERSION`、
  `app/version.py`、Git tag 和版本化 EXE 文件名共同标识。
- 不再用日期加修改说明作为正式版本控制方式。
- GitHub Release 只分发编译后的上传端 EXE 和对应版本 README。
- 源码通过公开 GitHub 仓库 clone，不再分发源码 ZIP、helper 单文件或日期式
  整合包。
- 公开仓库不得包含真实账号姓名、密码、DPAPI 密文、数据库、图纸、日志或

- 公开源码使用干净的 `v1.0.0` 初始历史；旧私有历史和旧审核仓库不进入公开
  分发。

## 20. 2026-11-20 每日检查与一键覆盖更新

- 正式上传端每天第一次启动时，在后台请求 GitHub 最新正式 Release。检查不得
  阻塞 Tk 主线程；当天已经尝试过时，不因重复打开窗口而反复联网。
- 只有 Release 的 `tag_name` 为稳定 `vX.Y.Z` 且高于当前版本时才提示更新。
  GitHub 草稿和预发布版本不进入自动更新。
- 最新版本必须包含 `CAXA-Drawing-Uploader-vX.Y.Z.exe`，且 GitHub API 为该
  资产提供 `sha256:` digest；缺少资产或 digest 时阻止下载。
- 发现新版时，按钮显示“下载 vX.Y.Z”。点击后自动下载并校验 SHA-256，校验
  失败不得执行或替换任何本地 EXE。
- 校验通过后直接覆盖当前正在使用的 EXE，并自动重启到新版。不得要求现场
  手工替换文件，也不得先启动另一个长期并存的版本再让用户自行处理。
- 覆盖由新版 EXE 的更新模式完成：等待旧进程退出，将旧 EXE 改名保留为
  `.old-时间戳` 备份，把新版复制到原路径并重新启动原路径。覆盖或新版启动
  失败时保留/恢复旧文件，并在界面或更新日志中明确报错。
- 更新过程不得删除用户配置、任务日志、待核实记录或已加载的业务文件。
